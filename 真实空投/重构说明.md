# 真实空投 1.21.1 — 重构说明（施工契约）

> 状态：**进行中**。本文既是重构方案，也是必须遵守的兼容契约。
> 1:1 原版快照：git tag **`dyairdrop-1.1.0-port-1to1`**（重构出问题随时可回滚对照）。

## 一、目标

在**不改变玩法机制**的前提下，把 260 个类 / 约 18,000 行的 MCreator 产物按 Java 最佳实践重写：

1. 结构与职责清晰（分层包 + 服务类，去掉 99 个静态 `*Procedure` 与历史并列版本）；
2. **服务端权威**：所有状态变更只在服务端发生，客户端只做渲染与输入；
3. 修复两个点名问题：**空投密码面板与其它模组的冲突**、**空投在 Xaero 地图上不显示**；
4. 性能：去掉每帧 NBT 解析、tick 全量扫描与重复构造；
5. 许可改为 MIT 全开源（原作者已授权 gem19910816 接手）。

## 三、现状诊断（重构前实测）

- 结构：`net.mcreator.dyairdrop` 下 `procedures` 99 个类（69 个是 `public static void execute`）、`init` 15 个注册类、`block` 91 个（含 model/renderer 混装）、`client` 15 个；全库 361 处 `static`、126 处 `if (world instanceof …)` 样板、107 处方括号内 `ResourceLocation` 构造。
- 历史并列版本仍在：`Flycode / Flycode2 / Flycode2neo / Flycode2neomap / Flycode2forceload / Flycode3 / Flycode3neo / Flycode3neomap / Flycode4`、`Planeticks / Planeticksneo`、`Check / Checknew / Checknewlite / Buttoncheck`、`Button0..9 / Buttonre1..6 / Buttondelate`。
- tick：9 个 `*ticks*Procedure`，8 个文件挂 `TickEvent.Post`；`AirdroplargeticksProcedure` 每 tick `getEntitiesOfClass` 扫实体。
- 渲染：`PannelScreen.renderBg` 每帧调 12 个 procedure，每个都读 `blockEntity.getPersistentData()` —— **客户端每帧解析 NBT**。

### 密码面板（点名问题一）——4 个根因

| # | 根因 | 证据 |
|---|---|---|
| 1 | **客户端本地又执行一遍服务端逻辑** | `PannelScreen` 等 4 个屏幕的每个按钮回调：`PacketDistributor.sendToServer(new PannelButtonPayload(...))` 之后紧跟 `PannelButtonPayload.handleButtonAction(this.entity, ...)`；而 `handleButtonAction` **没有 `isClientSide` 守卫**，直接跑 `Button*Procedure` / `ButtoncheckProcedure`（改方块、扣血、发消息、`setblock` 命令） |
| 2 | **静态共享 GUI 状态** | `PannelMenu.guistate` 是 `public static final HashMap`，屏幕再 `static` 持有；控件引用塞进去且从不清空，多面板/多玩家互相踩 |
| 3 | **靠每 tick 强关容器** | `PannelMenu.onPlayerTick` 里 `entity.containerMenu instanceof PannelMenu` → `ShutdownprocessProcedure`；`stillValid()` 未绑定时直接 `return true`。任何包装/替换 `containerMenu` 的模组（Curios、背包类、JEI…）都会让面板卡住或一开就被关 |
| 4 | **ESC 硬编码 + 输入全量转发** | `keyPressed` 里 `if (key == 256) this.minecraft.player.closeContainer()`；`EditBox` `setMaxLength(32767)` |

**更严重的是逻辑本身**：`ButtoncheckProcedure` 的解锁分支要求
`guistate.containsKey("text:password_panel")` 且 EditBox 内容非空（L105），
而 `guistate` 里的 EditBox **只存在于客户端** —— 服务端执行时该条件恒为 false，
于是**服务端的解锁/开箱/`open` 标记全部被跳过**，状态改动只发生在客户端（本地假象 + 随后被服务端同步回滚）。
这既是不兼容其它模组的直接原因，也是"多人下开不了箱"的根因。

### Xaero 地图（点名问题二）——死代码

`MobairdropticksProcedure` L111–132 在服务端用命令调度器执行
`addwaypointxaero @a <x> <y> <z> <name> <title> <color> 2 true`，并 `.withSuppressedOutput()`。

实测：实例内 40+ 个模组（含 Xaero 小地图 26.5.0 / 世界地图 1.46.0）**没有任何模组提供该命令**；
Xaero 用的是聊天分享前缀 `xaero-waypoint:` / `xaero_waypoint_add:` / `xaero_waypoint:`
（见 `xaero/common/events/ClientEvents.class`、`xaero/common/minimap/waypoints/WaypointSharingHandler.class`）。
所以这段代码永远静默失败 —— 地图上不会有任何标记。

## 五、专项修复一：密码面板

**服务端权威改造**

1. 新包 `network/payload/PanelActionPayload`：`{BlockPos pos, int action, String text}`（`text` 只用于输入类动作，长度上限 32）。
2. 客户端 `PanelScreen`：只做渲染与输入，按钮回调**只** `PacketDistributor.sendToServer(...)`；
   删掉屏幕里对 `handleButtonAction` 的本地调用；`EditBox` 不再进任何全局 map。
3. 服务端处理：校验菜单类型与坐标一致、玩家距离（≤ 8 格）、动作频率（简单令牌桶）→
   调 `PasswordService`（校验/设置）→ 结果写进方块实体 → `level.sendBlockUpdated(...)` + 反馈（错误消息/音效由服务端下发）。
4. 删除 `guistate`、`ShutdownprocessProcedure` 的 tick 强关；`stillValid()` 改为「同维度 + 方块未变 + 距离 ≤ 8」。
5. 键盘：删掉 `key == 256` 硬编码，走 `Screen#onClose` 标准流程；`EditBox` 限长并过滤非法字符。
6. 兼容性：不再抢占其它模组的键位与容器状态；JEI/Curios/背包类模组包装容器时行为正确。

## 六、专项修复二：Xaero 地图标记

保留机制（配置项 `mapcompat.enableglobalcoordinates` + 实体/方块实体的 `dymap` 标记语义），换掉实现：

1. 服务端在空投落地/被抢/被搜空时向**同维度相关玩家**发 `MapMarkerPayload(dim, x, y, z, label, color, ADD|REMOVE, ttl)`。
2. 客户端 `compat/xaero/XaeroMapCompat`：
   - 探测 `xaerominimap` / `xaeroworldmap`（`ModList.get().isLoaded`）；
   - **首选**反射：`xaero.common.XaeroMinimapSession` → 当前会话的 `WaypointsManager` / `WaypointWorld`，
     构造 `xaero.common.minimap.waypoints.Waypoint`（名称、缩写、坐标、颜色、类型=临时）加入当前集合；
   - **回退**：向本地聊天注入 `xaero-waypoint:<name>:<initials>:<x>:<y>:<z>:<color>:<type>:<set>`，Xaero 客户端会自行解析；
   - 记录已添加标记（按维度+坐标），收到 REMOVE / 空投销毁 / 玩家切换维度时清理；
   - 所有反射都在 try/catch + 版本探测内，失败只打一条日志，绝不影响主流程。
3. 小地图与世界地图都要生效（同一份路点数据，Xaero 两侧共用）。
4. 颜色按空投等级区分；名称沿用「箱子显示名」这一现有行为。

## 七、性能清单

- 渲染路径零 NBT：方块实体的展示状态在 `setChanged`/同步时解析一次，缓存到字段。
- tick 收敛：9 个 tick 过程合并为服务对象，按「每 N tick + 就近玩家 + 仅服务端」门控；`getEntitiesOfClass` 加半径与间隔。
- 常量：`ResourceLocation` 全部提为 `static final`。
- `Minecraft.getInstance()` 全部移入 `client` 包；通用逻辑不碰客户端类。
- `Performance.forceload` 默认值与语义**保持不变**（用户要求保留现有机制），仅在文档与日志中强化「服务器慎用」提示。

### 施工中自查发现并修掉的两个隐患

1. **地图标记会被误删**：`RandomizableContainerBlockEntity.isEmpty()` 会先展开战利品表，
   空投刚落地、还没人开箱时容器确实是空的 —— 直接用 `isEmpty()` 会让标记在落地约 1 秒后消失。
   现改为先用 `getLootTable() == null` 判断「战利品已生成」，再判断是否取空。
2. **面板「×」键语义**：原 `ButtondelateProcedure` 删位的同时把 `showlight` 置 0（玩家借此重试），
   重构初期漏了这一步，已补上。

### 已知风险（未实机验证）

- 面板：解锁成功后的 blockstate 替换（`setblock ... open[facing=...]{LootTable:...} replace`）沿用原命令格式，
  但**多人环境下未实测**；`valid` 占用锁与自动关窗（55 tick）同样只有静态推演。
- Xaero：反射链按 26.5.0 / 1.46.0 的 `javap` 签名编写，**换 Xaero 版本可能失效**（失败只停用集成、不影响空投）；
  路点回收依赖玩家与空投处于同一维度。
- 玩法主流程（定时空投、飞机航线、敌人抢夺、信号枪）本次未改动，仍以 1:1 移植版的启动级验证为准。

注册 ID、NBT 键、配置键、战利品表路径在 1.2.0 中**均未改动**，旧存档与 `dyairdrop.toml` 可直接沿用。
