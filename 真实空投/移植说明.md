## 三、改动清单

### 3.1 反编译与名字还原

1. Vineflower 1.10.1 反编译 1.20.1 jar → 256 个 `.java`（成员名为 SRG，如 `m_88315_`）。
2. 用 MCPConfig `joined.tsrg`（混淆名→SRG）与 Mojang 官方 1.20.1 映射按
   「类 + 混淆名 + 描述符」三元组求交，把本模组用到的 **473 个成员**全部还原为 Mojang 名
   （**0 未解析、0 歧义**）。

   > 注意：Mojang 映射文件里类名与描述符都用**点号**，而 `joined.tsrg` 用**斜杠**；
   > 两侧必须统一归一化后比对。不归一化会漏掉 58 个「描述符里带自定义类型」的成员
   > （例如 `ResourceLocation.parse`、`Item.TooltipContext` 那几类），
   > 这类成员正好是最容易出错的部分。

## 四、修掉的两个 BUG

### 4.1 密码面板：专用服务器上完全不可用

原版把面板文本框内容只存在**客户端**的 `guistate` 静态表里，服务端读到的是空串：

| 位置 | 原版行为 | 现在 |
|---|---|---|
| `ButtoncheckProcedure` 解锁判定 | 额外要求 `EditBox.getValue().length() > 0`；专用服务器上 `guistate` 为空 → **判定永远不成立，密码永远验证不了**（单机因为是同一个 JVM，静态表恰好可见，所以只在多人服务器暴露） | 改为 `!PanelText.from(guistate).isEmpty()` |
| `SetpwProcedure` 设置密码 | 从 `EditBox` 取值 → 服务端取到 `""` → 一直提示「长度错误」，**管理员无法设置/修改密码** | 同上 |
| `OpProcedure` 设置战利品表 | 同上，服务端存进去的是空串 | 同上 |

**修法**：按钮包携带文本框内容。

- `PannelButtonMessage` / `TestGUI2ButtonMessage` 增加 `text` 字段，4 个界面的 30 个发送点
  填入 `password_panel.getValue()`；
- 新增 `network/PanelText` 保存最近一次收到的文本；
- 过程里统一用 `PanelText.from(guistate)` 取值——**本地有控件时优先用控件（单人游戏行为与原版逐字节一致）**，
  否则用客户端随包发来的文本。

### 4.2 小地图：标记永远不出现

原版在空投落地时执行一条**并不存在的指令**：

```
addwaypointxaero @a <x> <y> <z> <名称> <名称> <颜色> 2 true
```

这条指令不是 Xaero 小地图提供的（`cafneoforge1.21.1` 与 0.51 整合包的全部 jar 里，
除本模组自身外没有任何文件含这个字符串），所以在装有 Xaero 小地图的环境里只会得到
「未知的指令」错误，**小地图上永远不出现空投标记**。

**修法**（新增 `compat/MapCompat`）：

1. **保留原指令但先检测存在性**：`Commands.getDispatcher().getRoot().getChild("addwaypointxaero")`，
   只有真有这条指令时才执行；没有就静默跳过，不再刷错误日志。
2. **内置原生支持**：按 Xaero 自己的路径点分享格式发送**系统聊天消息**
   ```
   xaero-waypoint:<名称>:<符号>:<x>:<y>:<z>:<颜色>:false:0
   ```
   格式逐字段取自 xaerominimap 26.5.0 的 `WaypointSharingHandler` / `onWaypointAdd`
   （名称 1–32 字符、符号 1–3 字符、冒号分段 ≥9 段）。Xaero 小地图会把这条消息渲染成
   「点击添加路径点」，于是**只装 Xaero 小地图就能看到空投标记**，不需要任何附加模组。
   名称里的 `:` 会先被剔除，避免破格式；即使格式不被识别，也只是一条普通聊天文本，不会崩游戏。
3. 相关移植修复：召唤指令的 `ForgeData` → `NeoForgeData`，否则 `dymap` 标志读不到，
   小地图功能连触发都不会触发。

### 4.3 密码面板与其它模组冲突（客户端执行服务端逻辑 + 用指令改方块）

**现象**：在整合包里输密码 / 开锁时容易和其它模组撞车，报告的例子是
**C2ME**（`[C^2M 引擎] c2me-neoforge-mc1.21.1-…`）这类**并发区块 / 方块实体优化**模组——
崩在区块或方块实体的并发访问上、方块实体被顶掉、状态不同步。

**根因**（读原版代码得到，共三处）：

1. **MCreator 的界面会「本地再执行一遍」服务端过程。**
   4 个面板界面的按钮回调都是「发包」之后**紧接着**本地调用
   `XButtonMessage.handleButtonAction(this.entity, id, x, y, z)`，
   也就是 **客户端也会跑一遍** `ButtoncheckProcedure` / `CheckProcedure` / `OpProcedure` / `SetpwProcedure`。
   这些过程里有 `world.setBlock(...)` 与方块实体数据读写，于是**客户端也在改自己的世界**：
   把箱子方块换成 `…open` 变体，等于在客户端销毁 / 重建一个带方块实体的方块。
   对任何盯着方块实体或区块的模组来说，这就是最典型的冲突点。
2. **改方块走的是指令通道。** 原版把箱子换成 `…open` 变体用的是
   `performPrefixedCommand("setblock ~ ~ ~ <id>open[facing=…]{LootTable:\"…\"} replace")`，
   会把「指令 / 方块放置 / 区块访问」上的所有模组都拉进密码面板的流程；
   而且 `setblock … replace` 会丢掉方块实体的其余数据。
3. **定时步骤不检查区块。** 解锁流程里 `queueServerWork(20/45/84, …)` 的 lambda 直接
   `world.getBlockState(pos)` / `getBlockEntity(pos)`，箱子所在区块恰好被卸载时就会拿到空值或抛错
   （区块优化模组会让这种情况更频繁）。

**修复**（新增 `compat/CrateCompat`，并改写过程与界面）：

| 改动 | 内容 |
|---|---|
| 新增 `compat/CrateCompat` | `openCrate(...)`：**仅服务端 + 区块已加载**才执行，直接用方块 API 换成 `…open` 变体（保留 `facing`），并把方块实体里的 `loot` 标签写成真正的 `LootTable`（等同于原来那条指令的效果，但不走指令通道）；`setBlockAnimation(...)` 同样带侧与区块检查 |
| `ButtoncheckProcedure` / `CheckProcedure` | 两处 `setblock … replace` 指令整块替换为 `CrateCompat.openCrate(...)`；动画用的 `world.setBlock(...)` 替换为 `CrateCompat.setBlockAnimation(...)` |
| `MobairdropticksProcedure` | 落地时放置箱子改为**仅服务端**（客户端也会 tick 这个实体，原来客户端会跟着改方块） |
| `PannelScreen` / `TestGUI2Screen` / `PannelREScreen` / `PannelRE2Screen` | 「解锁 / 设置战利品 / 设置密码 / 检查」这几个**整笔事务**按钮取消本地重复执行，只发包，服务端执行后由同步包回写界面（数字键盘按钮保留本地回显，不影响手感） |

**结果**：客户端不再改世界，也不再经指令通道改方块；密码面板在并发区块 / 方块实体类模组
（C2ME 等）下的冲突面被消掉。手感上的代价：解锁 / 设置密码 / 设置战利品要等一个往返
（约 1 个 tick）才看到反馈。

## 六、复现方式

### 6.1 Gradle（推荐，需要联网）

```powershell
cd 真实空投
.\gradlew build        # 产物 build/libs/dyairdrop-1.1.0.jar
```

### 6.2 本仓库成品 jar 与源码的一致性

`dyairdrop-1.1.0.jar` 由本目录源码直接编译打包（javac 21 + 同一套依赖），
`META-INF/neoforge.mods.toml` 由 `src/main/templates/` 的模板按 `gradle.properties` 展开得到，
与 `./gradlew build` 的产物等价（Gradle 侧不做 reobf，NeoForge 1.21.1 使用官方命名）。

### 6.3 移植流水线

本次移植使用了一套可复现脚本（反编译 → SRG 映射 → 机械迁移 → javac 编译 → 资源迁移 → 打包），
原文与中间报告保存在移植方工作目录，不在本仓库内。核心步骤：

1. Vineflower 反编译；
2. `joined.tsrg` + Mojang 映射求交得到 SRG→Mojang 表（含点号/斜杠归一化）；
3. 机械改写（上表 3.2）+ `manual/` 覆盖 45 个需要真改写的类；
4. `javac` 直接针对 NeoForge 官方 jar 编译（不依赖 Gradle 与联网）；
5. 资源迁移（目录单数化 + 配方/战利品表格式 + 标签）；
6. 打包并用官方服务端实机断言。
