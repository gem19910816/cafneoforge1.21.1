## 二、移植做法

### 2.1 整体判断：这是一次「加载器换代」，不是「功能重写」

上游这 44 个文件里，业务逻辑（体力公式、抑郁/疾病/恐慌阈值、职业分级表、掉落表）
一行都不用动 —— 它复刻的是 KubeJS 脚本的数值。真正必须改的只有四类东西：

1. **加载器 API**：`net.minecraftforge.*` → `net.neoforged.*`
2. **1.21 原版 API**：物品 NBT → 数据组件、事件 Phase → Pre/Post、`ResourceLocation` 构造
3. **网络层**：Forge 的 `SimpleChannel` 整套被 NeoForge 的 payload 体系取代
4. **数据包格式**：目录改名、配方 `result` 字段改名

于是策略是：**能不改的尽量用 cp 原样搬，要改的集中改**。实际结果是 44 个文件里
**8 个零改动直接复制**（`ProfessionConfig`、`ClientStaminaState`、`HudPositionConfig`、
`HudPositionScreen`、`StatusScreen`、`CafBackpack`、`BackpackCurioRenderer`、
`SatchelCurioRenderer`、`BackpackScreen` 中的大部分），其余逐个做定向改写。

### 2.2 加载器 API 对照

| 1.20.1 Forge | 1.21.1 NeoForge |
|---|---|
| `FMLJavaModLoadingContext.get().getModEventBus()` | **删除**，改构造注入 `@Mod(id) X(IEventBus, ModContainer)` |
| `MinecraftForge.EVENT_BUS` | `NeoForge.EVENT_BUS` |
| `@Mod.EventBusSubscriber` | 顶层 `@EventBusSubscriber`（`Bus.FORGE` 改名 `Bus.GAME`） |
| `ForgeRegistries.ITEMS/BLOCKS/ENTITY_TYPE` | `BuiltInRegistries.ITEM/BLOCK/ENTITY_TYPE` |
| `RegistryObject<T>` | `DeferredHolder<R, T>` |
| `ForgeConfigSpec` | `ModConfigSpec`（API 未变，纯改名） |
| `IForgeMenuType.create` | `IMenuTypeExtension.create` |
| `NetworkHooks.openScreen` | `ServerPlayer#openMenu` |
| `ForgeRegistries.ITEMS.getValue(rl)`（可返回 null） | `BuiltInRegistries.ITEM.get(rl)`（未注册返回 `Items.AIR`） |
| `DistExecutor.unsafeRunWhenOn(Dist.CLIENT, …)` | **删除**：改用 `@EventBusSubscriber(value = Dist.CLIENT)`，服务端根本不加载那个类 |

### 2.3 网络层重写（改动最深的一块）

Forge 的 `SimpleChannel` / `NetworkRegistry` / `NetworkDirection` / `NetworkEvent.Context`
在 1.21.1 已整套移除。改成：

- 每个包实现 `CustomPacketPayload`，自带 `TYPE`（`ResourceLocation`）与 `STREAM_CODEC`。
  无字段的包用 `StreamCodec.unit(...)`，不必再手写空编解码器。
- 全部 6 个包（4 个 S→C、2 个 C→S）在 `StaminaNetwork#register(RegisterPayloadHandlersEvent)`
  **一次登记完**，`event.registrar("1")` 只调用一次。
- 发送改静态：`PacketDistributor.sendToPlayer(...)` / `sendToServer(...)`，不再是
  `CHANNEL.send(PacketDistributor.PLAYER.with(...), pkt)`。
- 处理器签名 `(载荷, IPayloadContext)`；「切回主线程」由调用方
  `context.enqueueWork(...)` 统一做，`ClientPacketHandlers` 里不再自己调度。

**对外方法签名刻意保持不变**（`send` / `sendStatus` / `sendHudOpen` / `sendHudReset` /
`sendOpenBackpackPacket` / `sendScrollPacket`），所以业务代码里那些调用点一行没改。

### 2.4 背包持久化：`ItemStack` NBT → 数据组件

1.20.5 起 `getOrCreateTag()` / `hasTag()` / `getTag()` 全部移除。这里**刻意选
`minecraft:custom_data`** 而不是自定义数据组件：

```java
private static CompoundTag getTag(ItemStack stack) {
    CustomData data = stack.get(DataComponents.CUSTOM_DATA);
    return data == null ? new CompoundTag() : data.copyTag();
}
```

理由：1.20.5+ 的 DFU 会把老物品上的**未知 NBT 自动搬进 `minecraft:custom_data`**，
所以 1.20.1 存档里的背包内容（`Inventory` / `BackpackId` 两个键）**原样读得出来**，
一个字节的迁移代码都不用写。

顺带一处连带改动：1.21 的物品栈反序列化要注册表访问（数据组件要查注册表），
所以 `createHandler` / `saveHandler` 多带了一个 `HolderLookup.Provider` 参数，
由调用方从 `player.registryAccess()` 取。`ItemStackHandler.serializeNBT(provider)` 写出来
的仍是 `Size` + `Items` 两个键，与 1.20.1 完全同构 —— 这是老背包能读出来的另一半原因。

### 2.5 Curios 集成：capability → 接口

1.20.1 那套 `ICapabilityProvider` + `Capability` + `LazyOptional` 全部消失。Curios 9.x
的 `ICurioItem` 是**全 default 方法接口**，物品直接 `implements ICurioItem` 覆写
`canEquip` / `canEquipFromUse` 即可，`initCapabilities` 整个方法删掉。

`CuriosApi.getCuriosInventory(...)` 的返回值由 `LazyOptional<ICuriosItemHandler>`
变成 `Optional<ICuriosItemHandler>`，所以 `.resolve().flatMap(...)` 里的 `.resolve()` 要去掉。

`ICurioRenderer.render(...)` 的签名**与 1.20.1 逐参数一致**，两个渲染器零改动。

### 2.6 1.21 原版 API 细节

| 位置 | 改动 |
|---|---|
| 全局 | `ResourceLocation.tryBuild(ns,path)` → `fromNamespaceAndPath(ns,path)` |
| 体力/状态/生存/职业/钓鱼 | `TickEvent.PlayerTickEvent` 的 `Phase.START` → `PlayerTickEvent.Pre`，`Phase.END` → `PlayerTickEvent.Post`（一个方法拆成两个） |
| `ClientSprintBlocker` | `TickEvent.ClientTickEvent`（只剩 END）→ `ClientTickEvent.Post` |
| `TentChannelHandler` | `TickEvent.ServerTickEvent` → `ServerTickEvent.Post`；`state.use(...)` → `state.useWithoutItem(...)`（1.21 把 `use` 拆成 `useItemOn`/`useWithoutItem`，收起帐篷那条路手里确定是空的，所以走后者） |
| 各交互处理器 | `event.getSide().isClient()` → `event.getEntity().level().isClientSide()`（等价，且不依赖那个已被挪走的辅助方法） |
| `PanicSystem` / `PoopSystem` | `stack.isEdible()` → `stack.has(DataComponents.FOOD)` |
| `PoopSystem` | `stack.getTag().getString("ConsumableId")` → 走 `DataComponents.CUSTOM_DATA` |
| `StaminaHud` | `IGuiOverlay` + `ForgeGui` + `RegisterGuiOverlaysEvent` → `LayeredDraw.Layer` + `RegisterGuiLayersEvent`；渲染签名变 `(GuiGraphics, DeltaTracker)`，屏幕尺寸从 `g.guiWidth()/guiHeight()` 取 |
| `BackpackClientRegistration` | `MenuScreens.register` 在 1.21.1 已不可从外部调用 → 改走 `RegisterMenuScreensEvent` |
| `ShitballEntity` | `ForgeRegistries.ITEMS.getValue()` 的 null 判断改成与 `Items.AIR` 比较 |
| `MilitaryBackpackItem` | `appendHoverText` 第二个参数 `Level` → `Item.TooltipContext` |

### 2.7 数据与资源

- `data/caf/recipes/` → `data/caf/recipe/`
- `data/curios/tags/items/` → `data/curios/tags/item/`
- 配方 `result` 由 `{"item": …, "count": …}` 改成 `{"id": …, "count": …}`
  （**只有 result 改；`key` 里仍是 `{"item":…}` / `{"tag":…}`** —— 这一点是拿 1.21.1
  原版 jar 里的 `stick.json` / `acacia_boat.json` 逐字核对的，不是猜的）
- `pack.mcmeta` 的 `pack_format` 15 → 34，并把描述里的 `${mod_id}` 占位符写实
- `META-INF/mods.toml` → `META-INF/neoforge.mods.toml`：`loaderVersion="[4,)"`，
  `mandatory=true` → `type="required"`

### 2.8 一个必须记下来的 NeoForge 行为差异

上游主类里有一行 `forgeBus.register(StaminaItems.class);` —— 那是个**无副作用的空操作**
（`StaminaItems` 只有 `DeferredRegister` 字段，没有任何 `@SubscribeEvent` 方法），
Forge 当年静默放行。

**NeoForge 的事件总线对此直接抛异常**：

```
java.lang.IllegalArgumentException: class com.chaosz.tarkovstamina.item.StaminaItems
has no @SubscribeEvent methods, but register was called anyway.
```

第一次开发环境启动就死在这里。这不是编译期能发现的（编译通过），
**只有真的把服务端拉起来才会暴露**。已删掉那一行并加注释说明。

## 四、已知事项与未验证范围

### 4.1 尚未验证（重要）

本次验证只到**「模组能加载、服务端能起」**这一层。以下**全部没有实机跑过**：

- **客户端**：`runClient` 没启动过。体力 HUD 的渲染层（`StaminaHud`）是从
  `IGuiOverlay` 改成 `LayeredDraw.Layer` 的，**这是本次改动里风险最高的一处** ——
  注册方式、渲染签名、屏幕尺寸来源三样都换了，编得过不代表画得对，必须实际进游戏看。
- **背包 GUI**：`BackpackScreen` 的 `inventoryLabelY` 等受保护字段、以及
  `RegisterMenuScreensEvent` 这条新路径，都要开界面才能确认布局没歪。
- **Curios 背部渲染**：两个 `ICurioRenderer` 虽签名未变，但要装上背包看模型朝向。
- **玩法主流程**：体力消耗/恢复、抑郁/疾病/恐慌/成瘾的计时、职业分级、
  钓鱼咬钩、排泄、帐篷读条 —— 一个都没跑过。
- **老存档兼容**：`custom_data` 那条路是**按 DFU 的行为推断**的，没有用真实 1.20.1
  存档里的背包实测过。
- **多人并发**、专用服务器上的 `ClientPacketHandlers` dist 隔离（编译期没问题，
  但"服务端不会加载那个类"这条只做了代码结构上的保证，没在真实双端联机里验过）。

### 4.2 环境约束（不是移植缺陷，但接手的人必须知道）

- **本机无外网**，所以 `ModDevGradle` 固定 **2.0.107**、NeoForge 固定 **21.1.227**
  （`通用\gradle-home` 缓存里只有这两个）。上游用的 2.0.143 / 21.1.248 取不到。
  NeoForge 21.1.x 是稳定分支、API 只增不减，所以编译版低于上游不影响代码；
  想对齐上游时改 `gradle.properties` 里的 `neo_version` 即可，源码不用动。
- Curios 走 `libs\` **flatDir** 而不是 maven 坐标，同样是因为没网。
  有网后可换成 `maven.modrinth:curios:9.5.1+1.21.1`。

### 4.3 设计上的保留决定

- **`mod_id` 没改。** 上游文件夹叫 `tarkov_stamina_mod`、显示名要改成中文，
  但 `mod_id` 一动，现有存档挂在 `persistentData["tarkov_stamina"]` 下的体力、
  注射次数、锻炼等级、职业计数**全部归零**。所以 id 保持不变，只改显示名。
- **Curios 仍是硬前置。** 沿用上游 `mandatory=true` 的语义。背包的背部槽位、
  以及"从饰品栏找回背包"那条路径都直接调 `CuriosApi`，放宽成 optional 会变成
  运行期 `NoClassDefFoundError`，比拒绝启动更难排查。
- **版本号 `1.0.0-port`。** 上游是 `1.0.0`，加 `-port` 后缀是为了和原版 jar 区分开。

## 五、代码审查：无用代码、失效配置与功能空洞

移植完成后对整个 `src/main/java` 做了一遍静态审查（未使用符号扫描 + 配置项读写配对 +
注册 id 与语言键对照）。下面按「要不要动」分类。

### 5.1 已修（零风险，默认行为不变）

| # | 问题 | 处置 |
|---|---|---|
| 1 | `item.caf.bijibendiannao` **缺翻译键** —— `StaminaItems.LAPTOP` 注册了这个 id，但 `zh_cn.json` / `en_us.json` 里都没有对应条目，游戏里物品名会**直接显示原始键名** `item.caf.bijibendiannao` | 已补（zh：技能终端 / en：Skill Terminal） |
| 2 | `DepressionSystem` **忽略了自己的配置项** —— `StaminaConfig.DEPRESSION_SLEEP_TICK_LIGHT` 声明了却从没被读过，代码里是硬编码 `36000` / `18000`，玩家改配置没有任何反应 | 已把 `LIGHT` 接上（默认 36000 / 36000÷2，与原字面量一致，**行为不变**） |
| 3 | `ProfessionSystem.incrementCount` 里 `data.putInt(key, count)` **连写两遍**（同一行重复） | 已删重复行 |
| 4 | `ProfessionSystem.calcAmplifier(...)` 死方法（private，全工程无人调用；阶级的 amplifier 实际是拿 `i + 1` 当等级用的） | 已删 |
| 5 | `FishingSystem` 里 `import com.chaosz.tarkovstamina.StaminaSystem;` **未使用**（上游就有） | 已删 |

### 5.2 已用注释标注、但**没动**（属于玩法 / API 决定，不该在移植里顺手改）

1. **`StaminaConfig.DEPRESSION_SLEEP_TICK_HEAVY` 仍是空配置。**
   它的注释写着「不睡 72000 tick 触发重度抑郁」，但这套 `factors` 计数逻辑里根本没有
   「光靠熬夜就进重度」这条路径 —— level 100 要求 `factors >= 2`，也就**必须**同时满足
   「室内幽闭」。这是上游设计没落地，不是移植丢的。

2. **`StaminaConfig.MAX_MINING_LEVEL` / `MINING_PROGRESS_PER_BREAK` 完全无效。**
   上游把挖掘系统整个删了（见 `ExerciseSystem` 注释：「挖掘系统已移除，石工职业已覆盖
   挖掘速度加成」），但这两项配置留了下来，且全工程无人读取。配套地，
   `StaminaSystem` 还在往存档里写 `miningProgress` / `miningLevel` 两个死键。
   保留是为了不改动已有配置文件的键集合；要清干净得连存档键一起定。

3. **`ProfessionConfig.AMPLIFIER_NAMES` 死常量 —— 刻意没删。**
   该文件是**逐字节照搬上游**的（零改动文件之一），保持原样是为了以后要跟上游做 diff
   时干净。删它没有收益，却有代价。

### 5.3 功能空洞（上游就有的，不是移植丢的）

**打伞防感冒这条功能是死的。** `DiseaseSystem` 用 `caf:umbrella` 判断手里有没有伞，
但**本模组从来没注册过这个物品**，也没有任何别的地方提供它 —— 在 1.20.1 上它是靠
整合包的 KubeJS 脚本注册的。1.21.1 没有 KJS 桥接，所以现在**没有任何办法避免淋雨感冒**。

同理，`PoopSystem` 医疗食物白名单里的 `caf:ganmaoyao` / `caf:jieyanyao` / `caf:jiejiuyao`
三个 id 也都没人注册，那三行白名单是空转。

另外两组「定义了但永远看不到」的语言键：
- `hud.tarkov_stamina.stamina` / `.sprinting` / `.recovery_delay` —— 代码从不引用，
  只有 `.exhausted` 在用。
- `item.caf.special_strength_injection.desc` / `body_monitor.desc` / `shit.desc` ——
  这些物品都是**素 `Item`，没有任何 `appendHoverText` 覆写**，所以这三条描述
  **永远不会显示**。

补 `caf:umbrella` 和那几个药品物品属于**加功能**，不是移植范围，故未做。

### 5.4 保留的公开 API（看着「无用」，但没删）

以下在本工程里都没有调用点：

```
StaminaSystem.staminaFraction / getInjectionCount / getExerciseLevel / getMiningLevel / isOverweight
PanicSystem.recordConsumption
BackpackMenu.getBackpackScroll
StaminaConfig.DEPRESSION_SLEEP_TICK_HEAVY（见 5.2）
```

上游是留给 KubeJS 脚本调的（注释写着「供 KJS 或其他系统调用」）。**没删的理由**：
它们是 `public`，删掉等于对第三方附属关门，而这类脚本入口留着的成本是零。
如果确定不要第三方接入，可以再清一轮。

### 5.5 性能观察（不是 bug，但值得知道）

1. `StaminaSystem` 每个玩家**每 tick** 发一次 `StaminaSyncPacket`（20 包/秒/人），
   没有做「值变了才发」的门控。
2. `BackpackMenu.broadcastChanges` 每次广播都把整个背包序列化成 NBT 写回物品栈。
3. `PoopSystem.onTick` 没有 `% N` 取模门控，每 tick 都跑（其余系统都有 5 / 20 / 100 的
   门控）。
4. `WeightSystem` 每 5 tick 扫 36 个背包格。

以上都是上游原有行为，本次未改动；人多了要优化就从这四处下手。

### 5.6 扫描里的两处「看着像问题其实不是」

- `HudConfig.HUD_GROUP_CLOSED` 是「赋给常量以触发静态初始化」的惯用写法
  （`closeHudGroup()` 里做 `BUILDER.pop()` / `push()` 切分组），设计如此，不是死代码。
- 第一版扫描把 `HudConfig` 自己的 `LEFT` / `BOTTOM` / `WIDTH` / `HEIGHT` / `SCALE` /
  `SHOW_ONLY_WHEN_CHANGED` / `BAR_COLOR` 报成「没被读取」，那是正则误报 ——
  它们在 `HudConfig` 内部以 `LEFT.get()` 形式使用，不带类名前缀。

### 5.7 实测发现的移植回归：背包界面的悬停提示不显示（已修）

**症状**：打开背包后，鼠标悬停在格子里的物品上**不弹任何提示**；同一个物品在普通
玩家背包里悬停却正常。（物品本身显示正常、格子高亮也正常，只是没有信息框。）

**根因**：1.21 把「画悬停提示」这件事**从基类挪到了每个具体界面**。

| | 谁负责调 `renderTooltip` |
|---|---|
| 1.20.1 | `AbstractContainerScreen.render()` 结尾自己调，子类**白拿** |
| 1.21.1 | `AbstractContainerScreen` **只剩定义、零调用点**；由每个具体界面在自己的 `render()` 里调 |

证据是 1.21.1 原版源码：`ShulkerBoxScreen`、`ContainerScreen`、`InventoryScreen`、
`HopperScreen`、`CraftingScreen`…… 原版**每一个**容器界面都写着

```java
public void render(GuiGraphics g, int mouseX, int mouseY, float partialTick) {
    super.render(g, mouseX, mouseY, partialTick);
    this.renderTooltip(g, mouseX, mouseY);   // ← 1.20.1 时这行在基类里
}
```

而 `AbstractContainerScreen.renderTooltip(...)` 全文只出现两次：一次是它自己的定义，
一次是它内部调用 `GuiGraphics.renderTooltip`。**没有任何地方调它。**

**为什么移植时漏了**：`BackpackScreen` 是从上游逐行搬的，上游在 1.20.1 上不需要这个
覆写；编译也不会报错（`renderTooltip` 是有默认实现的 protected 方法，缺了它只是
"少画一层"）。**这是编译器抓不到、只有真进游戏点开界面才看得见的一类回归。**

**修复**：给 `BackpackScreen` 补上 `render()` 覆写。

```java
@Override
public void render(GuiGraphics g, int mouseX, int mouseY, float partialTick) {
    super.render(g, mouseX, mouseY, partialTick);
    this.renderTooltip(g, mouseX, mouseY);
}
```

**同类风险提示**：本模组另外两个自绘界面 `StatusScreen` 与 `HudPositionScreen` 继承的是
普通 `Screen`（不是 `AbstractContainerScreen`），界面里没有任何物品槽，不涉及这条路径。

### 5.8 实测发现（上游就有的）画错：军用背包「玩家背包区」底图被拉长 2 像素（已修）

**症状**：军用背包（12×9 宽版）界面里，玩家**快捷栏那一行有一条横穿格子的黑线**，
而且鼠标悬停时**白色框选与底图格子对不上**。

**根因是宽版分支里那段玩家背包区背景的算术错误。** 先把原版数据核准
（读 1.21.1 的 `ChestMenu` 与 `ContainerScreen` 源码）：

| 量 | 原版 | 本模组（宽版） | |
|---|---|---|---|
| 玩家槽相对底图原点 x | 8 | 7 | ✗ 差 1 |
| 主背包槽相对底图原点 y | 14 | 14 | ✓ |
| 快捷栏槽相对底图原点 y | 72 | 72 | ✓ |
| 底图高度 | **96**（源 y 126..221） | 三段拼 73+18+7 = **98** | ✗ 多 2 |

原版是**一次**画完：

```java
// ContainerScreen
blit(TEXTURE, i, j + containerRows * 18 + 17, 0, 126, imageWidth, 96);
```

上游在宽版分支里把它拆成了三段（高 73 / 18 / 7），而源纹理那一段只有 96 行 ——
**96 行源塞进 98 行目标，底图被整体拉长 2 像素**，越往下偏得越多。快捷栏正好在最底下：

- 底图的格子被推低 2 像素，而玩家槽位的白色框选画在**真实**槽位（y+200 / y+258）上
  → 框选与底图对不上；
- 三段之间的接缝还把源 y=197 那行深色分隔线**多画了一次**，落进快捷栏格子内部
  → 那条横穿快捷栏的黑线。

**修复**：照抄原版，一次画完 96 像素；起点 x 由 36 改为 **35**，让底图的槽格（源 x=8）
正好落在真实玩家槽位 x+43 上（43−8=35）。

```java
int playerX = x + 35;
int playerY = y + 24 + rows * 18;
g.blit(CONTAINER_TEXTURE, playerX, playerY, 0, 126, 176, 96, 256, 256);
```

**小背包（非宽版）分支本来就是对的**，没动：它的玩家背包区是一段 96 像素、起点在
`y + 17 + rows*18`，相对偏移正好是 8 / 14 / 72。这也解释了为什么只有军用背包出问题。

**这是上游 1.20.1 版就有的错**（同一段代码），不是移植引入的 —— 移植时逐行照搬，
连错一起搬过来了。

## 六、构建方式

```
build.bat build        # 编译并打 jar
build.bat runClient    # 开发环境客户端（游戏目录 run\）
build.bat runServer    # 开发环境服务端
build.bat runData      # datagen
```

- 构建环境：**JDK 21 (21.0.3) + Gradle 8.8 + ModDevGradle 2.0.107 + NeoForge 21.1.227**
- `build.bat` 指向 `通用\gradle-8.8` 与 `通用\gradle-home`（共享依赖缓存），
  文件编码 **GBK + CRLF**（按《mod制作文件管理规范与指南》第六节）
- 跑 `runServer` / `runClient` 前，把 `libs\curios-neoforge-9.5.1+1.21.1.jar`
  复制到 `run\mods\`，否则因 Curios 是硬前置会被拒绝加载
- 产物：`build\libs\tarkov_stamina-1.21.1-neoforge-1.0.0-port.jar`
  已随附到 `mod保存\1.21.1neoforge\CAF生存核心\`

编译**离线可复现**：加 `--offline` 跑得通，全程不碰网络。
